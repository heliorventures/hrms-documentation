# Strict release of existing running services

`online-release.py` is a separate protected operator entrypoint. The ordinary `deploy-on-vps.ps1`, full-startup release, renderer and build scripts are unchanged. This helper performs no image build/load, database migration, grant/revoke, secret reconciliation, source activation, Caddy reload or business-data restore. Images must already be loaded and independently reviewed.

## Approval and immutable inputs

Prepare and review a complete plan before any execution. Pending build/image/fleet/probe bindings are not executable inputs. The actual release-007 plan remains pending root's final images, fresh fleet and Sol then Astra review. No production plan or launcher is provided here.

The future root invocation requires explicit `--apply`, a plan path and its exact SHA-256. The executor itself must already be installed as a root-owned regular `0600` file at a canonical path and match `executorSha256`. The private operator package is root-owned, source-validated and pinned by its package hash. Both its existing operator lock/deferred-termination context and the standard `/run/lock/hrms-release.lock` are held throughout transition, replacement and recovery.

Plan fields:

| --- | --- |
| version/tag/appDir | version 1, reviewed target tag, exact `/opt/apps/hrms` |

| policyCompanies | exactly five `{database,schema,tenantId}` company tuples, matching all five rows in the protected registry receipt; company database identifiers, canonical lowercase UUIDs and tenant_UUID8 schema binding are strict |
| operator | protected `/root/hrms-private-config-*` directory and exact packageSha256; package sources also verified |
| oldArtifacts | every current public artifact path and hash, including compose/release/checksum |

| newArtifacts | exact reviewed output hashes for compose.json, release.json and release.sha256; executor recomputes before publication |
| baselineFleet | all running and stopped containers using `fleet_snapshot` below; no omitted containers |
| selected | unique ordered objects: service, phase (`backend`, `gateway`, `ui`), exact oldImage/newImage IDs, repository, exact oldImageReference, reviewed oldRepositoryTag and explicit readiness probe IDs |
| sourceReceipt/grantsReceipt | protected root path/hash; grants receipt must confirm the five-company business-column package completed with allRequired proofs |

Each selected service must be one of the 23 Rust, two gateway or two UI candidates and must already be uniquely running in project `apps` at its exact old image. Unknown, stopped, absent or dormant selections fail. The helper does not start dependencies or any unselected service. A gateway phase waits for the Employee schema gate; UI waits for the gateway schema gate. Every service has explicit readiness assertions and bounded probe retries. A single-replica recreation can briefly interrupt its endpoint; zero downtime is not claimed.

Image-family identity is explicit for every release. Tagged input must equal its reviewed oldImageReference and belong to the expected repository; digest input must equal oldImage. Native preflight verifies the retained oldRepositoryTag actually appears on that immutable image and resolves to oldImage, and resolves the current Compose reference independently. Thus a previous successful digest-based output is accepted as the next release's input without treating an unproved digest as a repository identity. Keep reviewed repository tags and old immutable images available for later rollout/recovery.

## Fresh fleet and private environment checks

The read-only collector can import `fleet_snapshot(items)` and supply metadata from `docker inspect` for **all** containers. The function exports only ID, image, running/start/restart state, Compose service/project and one contract digest covering command/entrypoint/user/working directory, mounts, networks and HostConfig. It does not consume or export Config.Env. Its exact source must be pinned by the collector/review package. Duplicate candidate service containers are rejected.

Inside the future operator process, actual selected environments remain only in memory. Before publication, Compose resolves each intended single-service model privately; pinned image environment defaults are combined with its resolved environment, then compared exactly with the existing container environment. The intended command, entrypoint, user, working directory, mounts, networks, published ports and host security flags are also checked before recreation. Every readiness boundary rechecks actual environments and the full fleet. Any changed or unprovable field fails closed. Environment values and environment hashes are neither stored nor printed; success reports only `environmentUnchanged:true`.

The public root Caddy file uses a separate reader for exactly `/opt/apps/Caddyfile`. Its reviewed fresh owner/group, `0644` mode, inode, device, positive bounded size and content hash must all match the plan. The reader rejects aliases, opens with `O_NOFOLLOW`, requires a regular file, compares descriptor metadata before and after reading, and verifies the path still refers to that exact file. It does not change ownership or grant a general exception for UID1000. The root-only `protected()` reader remains unchanged for all other files, secrets, receipts and executor sources. Native context also requires the exact preserved Caddy container ID/image, its running state and the unique matching source bind's destination/RW value before reading the active configuration through that container ID. The canonical active configuration hash remains required. Fresh collected metadata is evidence for preparing the plan; it does not authorize changing the proxy.

Host preflight compares supported capability additions/drops, security options, memory/reservation/swap/swappiness, pids, CPU shares/period/quota/realtime/nanocpus/cpusets, OOM settings, init/restart, ulimits, tmpfs, user/pid/UTS isolation, groups and sysctls before any public write. Engine-dependent runtime/IPC/cgroup/shared-memory/logging/DNS/default-path fields require the independent protected default contract and unchanged engine/Compose fingerprint. Bind mounts additionally require its explicit BindPropagation default and exact propagation/host options; legacy bind syntax and unmapped bind flags are refused. That receipt cannot override core mapped fields such as CapDrop or memory. Unknown actual HostConfig fields, unsupported Compose resource options and unsupported nondefault devices/storage/IO options are refused; they must receive a source-grounded mapping/review before use. This intentionally fails closed where private live metadata differs from the public model. Explicit command:null and entrypoint:null inherit the pinned image defaults; empty arrays remain explicit overrides.

Compose runs with `/dev/null` as its interpolation env file and a fixed subprocess environment. Runtime env files explicitly named by the already reviewed public service model are consumed privately by Compose; no local `.env` inspection is performed during preparation. The unresolved public single-service model is the only model saved in the root journal. The resolved model and Docker Config.Env remain private memory.

## Transition, probes and receipts

The pure transition changes only selected service image fields, release tag and the complete checksum index. All other public artifact bytes and all other Compose fields are preserved. Reviewed output hashes are required before CAS publication. The helper repeatedly checks all public files and all unselected containers. Execution uses a private single-service model referencing only the verified existing networks as external resources; missing/replaced networks fail, and Compose cannot create them. Bind sources must already exist canonically with create_host_path false; anonymous image mounts and unsupported Compose resource definitions are refused. The actual command selects exactly one service with `up --detach --no-deps --no-build --pull never --force-recreate`.

Probes run a fixed read-only Node fetch program in the pinned existing image/network, with all capabilities dropped, no privilege gain, read-only root, bounded process/memory/time limits and no Docker logging. No arbitrary shell/executable probe is accepted. Specify expected status plus exact text, body hash or JSON path assertions. POST is restricted to explicit GraphQL `query`; mutation/subscription text is refused. Schema gates must request complete SDL/types and bind the exact response hash. Source-derived probe documents, URLs and response criteria must be reviewed for each real release; no endpoint is inferred automatically.

A probe may set `networkKey` to one key from `probeNetworks`. Unknown keys or malformed name/ID bindings fail before any operation. With no `networkKey`, the existing `probeRuntime.network` and `networkId` remain the default. Every probe attempt checks its selected existing network's actual ID, then starts the same pinned Node image on exactly that network ID. Using the ID also prevents a replacement network with the same name from being selected between inspection and execution. This permits reviewed probes across isolated application networks without creating networks, joining multiple networks, or attaching existing containers. Recovery probes use the same selection rule. Network reachability and response assertions still require explicit review.

Preflight probes must assert the current old versions' readiness/public behavior, not the new image contracts. Failure prevents public intent, publication and every replacement. Recheck context/fleet afterward. A negative GraphQL boundary probe may use `expectedErrorCodes` only with kind `http`, query-only POST and expectedStatus200. Bind 1–8 ordered uppercase codes (`[A-Z][A-Z0-9_]{0,63}`); no mixed text/hash/JSON-path assertions. Success requires response `data` exactly null and an errors array whose ordered extensions.code list matches exactly. Missing codes, extra errors, partial data or wrong status fail. Positive POST probes always reject GraphQL errors. The fixed program exports no response/error content. Full employee/gateway schema body-hash requirements are unchanged.

Existing approved sessions may be supplied through an optional root-owned `0600` `headersFile` path/hash; inline session headers are forbidden. Session values and response bodies never leave the probe/operator memory; stdout contains only a boolean result. The helper provides no account/session creation or mutation acceptance.

The exclusive root `0700` journal records the frozen plan, public intent/hash manifest, unresolved private single-service models, per-service replacement intent/completion, rollback intent/completion, and final completion or failure. JSON receipts are exclusive `0600` files with fsync; public replacement files and publication directory are fsynced and read back. The journal path is printed before operations for protected operator retrieval. Raw command output, credentials and exception details are suppressed.

Plans must declare `contractFingerprintVersion:2`. Fingerprints sort runtime mounts by Destination and HostConfig mounts by Target after refusing duplicate targets. Every mount entry and option is retained; aliases, primary network, security settings and other arrays remain exact. Compose assembles mounts from a map, whose iteration order is not a contract ([Compose source](https://github.com/docker/compose/blob/v2.39.1/pkg/compose/create.go#L878-L930)). A local create-only reproduction produced two raw fingerprints but one normalized fingerprint with only mount order changed. Version 1 baseline hashes cannot be relabeled or reused as version 2; obtain and review a fresh baseline before execution.

The initial context also stores `contract-baseline.json` with complete version 2 selected-service contract values in the root-only journal. It excludes Config.Env and is not a public/downloadable receipt: configurable host options can contain private values. Failure receipts retain separate primary and recovery stage, service, probe, fixed allowlisted error code and safe error type. Unknown exception text is never exported, including uppercase text. Recording a failure location does not authorize a retry or recovery.

## Reviewed recovery and partial failure

Automatic image/config recovery requires a protected compatibility receipt with all of: `applicationRollbackCompatible:true`, `newWritesCompatible:true`, `businessDataRestore:false`, `grantsRetained:true`, the exact sourceReceiptSha256 and exact selected objects. The helper never creates this receipt. Review must cover writes made by the new version; a blanket permission to restore old images is insufficient.

The receipt must also contain exactly `policyGuard:{version:1,executorSha256:<plan.policyExecutorSha256>,companies:<exact plan.policyCompanies>,unchangedPolicyRequired:true}`. Missing, extra, mismatched or unconditional policy bindings are refused. Its new-write compatibility assertion is therefore conditional on this specific reviewed guard and unchanged policies, rather than an unconditional promise that new bounded grants remain safe under older code.

An additional policy continuity guard is mandatory because older backends may interpret a newly saved bounded grant more broadly. Before public intent/publication, capture a server-side SHA256 of the five RBAC metadata tables (`role`, `permission`, `role_permission`, `permission_scope`, `user_role`) in every open company database. Sorted JSONB aggregates are hashed inside PostgreSQL with built-in sha256; no policy rows are returned. Initial capture briefly acquires the exact `company-account-admin:{tenantUUID}` advisory transaction lock plus SHARE table locks on all five tables, then releases its owned sessions. Normal online policy changes remain allowed after capture; they make automatic rollback unavailable.

Capture and every rollback check first read the postgres control catalog for all five databases' OID/admission/connection-limit/template facts. A database with admission closed or connection limit zero must have zero sessions; do not open it or connect to it. Closed databases must remain closed with unchanged OID/admission and zero sessions before and after recovery. Open database identity/admission changes also refuse recovery. Tuples are validated against every active postgres registry row; no company may be omitted.

Before the first old replacement, reacquire every open company's advisory and five SHARE locks in deterministic database order, compare policy hashes, and hold all locks through every old replacement, artifact restoration, final probes and checks. SHARE locks block even legacy create/provision/prejoining user_role writes that do not take the advisory lock. Each boundary verifies the same backend, transaction, read-only status, exact advisory lock, all five granted ShareLocks and unchanged hash/catalog. Sessions use only the protected operator's verified PersistentPsql API with BEGIN READ ONLY, bounded lock/statement timeouts and fixed read/hash/lock SQL. No MaintenanceSession admission barrier, database-open operation, group/role/DML/DDL change, peer session termination or policy reversal is used. Cleanup rolls back/closes only owned clients; cleanup or liveness failure means operator review, even if images/public bytes were already restored.

Policy drift refuses automatic rollback before any old image runs and preserves legitimate grants and business data. A successful guard does not preserve the new authorization implementation: restoring old images still restores their older security behavior when the baseline policy is unchanged. This limitation must be disclosed in the reviewed recovery plan and final rollout approval.

On failure, the helper first verifies protected context, public bytes and all fleet contracts. It permits recovery only if attempted containers still have a known old/new image and unchanged source contract and all preserved containers remain exact. It restores attempted services in the explicitly reviewed rollback order, requiring each old-service readiness probe, restores exact old public bytes and runs final rollback acceptance. Grants and business data are retained throughout.

Unknown images, foreign contract changes, unexpected new containers, altered public files, missing compatibility evidence, failed rollback or ambiguous publication/commit state produce `ONLINE_RELEASE_OPERATOR_REVIEW_REQUIRED`. The protected journal records the attempted subset and incomplete recovery; it does not claim success or retry automatically. Public files left at the new generation during an incomplete recovery must be reconciled from receipts before any later rollout. A successful reviewed rollback reports `ONLINE_RELEASE_ROLLED_BACK` and remains a failed release.

### Explicitly reviewed partial-release continuation

A version 2 `resume` binding requires the pinned `online-release-resume.py`, original plan and unchanged execution journal, original readback, separately reviewed fresh observation, complete protected contract baseline, original policy baseline and a compatibility receipt for exactly the remaining services. The completed services must be an exact initial prefix of the original selection. All other lifecycle/image facts remain bound to the original run; the fresh observation must have independently verified the declared environment and security context and the original role policy. A new fingerprint baseline is an operator review decision, not proof that a discarded old raw contract has been reconstructed.

The validator derives every permitted plan change from those receipts: remaining services/order, already-published public hashes, version 2 fleet fingerprints and old-version probe adaptation for completed services. Probe definitions, image identities, source bindings, company tuples, preserved files and Caddy bindings cannot change. Historical `oldImageReference` values retain their original-plan image-family proof; the current published model already contains the reviewed new image IDs.

Continuation captures policy under the existing guard and requires exact equality with the original protected baseline before any replacement. It never resets that baseline. It does not load images, republish public files or recreate the completed prefix. Recovery can restore only the attempted remaining services, under the same unchanged-policy locks, to the observed starting partial state; the completed prefix and already-published public files stay intact. Both the continuation and that recovery scope require an exact operator review. Never replay the original failed bundle.

## Local validation

Host preflight treats absent/null empty Docker collections as empty only for their declared list or map type; nonempty neutral values and incorrect collection types are refused. Dynamic DNS/path lists and nested logging Config use the same typed empty equivalence while preserving every nonempty value and log driver. Docker's omitted or zero memory-swap setting derives a total allowance of twice a positive memory limit; explicit positive or unlimited swap settings remain exact. See [Docker resource constraints](https://docs.docker.com/engine/containers/resource_constraints/#--memory-swap-details). Unknown host fields still fail closed.

Run native commands from the workspace: `py -3 hrms-documentation/scripts/deploy/test_online_release.py`, `py -3 hrms-documentation/scripts/deploy/test_online_release_policy.py`, and `node hrms-documentation/scripts/deploy/test_online_release_probe.cjs`.

Mount/failure regressions: `py -3 hrms-documentation/scripts/deploy/test_online_release_contract.py`. Continuation regressions: `py -3 hrms-documentation/scripts/deploy/test_online_release_resume.py`. These synthetic tests prove control flow and refusal behavior; they do not demonstrate a running production recovery.

The synthetic suite covers pure image-only transition and two consecutive digest-based releases, retained repository identity proof, preserved/dormant services, main argument/hash flow, strict phase/schema gates, serial replacements, known partial recovery, failed/ambiguous rollback, complete supported host drift before publication, positive explicit limits, unknown/default-contract refusal, null command/entrypoint inheritance, exact new hashes, safe Compose flags, fixed read-only probes, secret-free fleet receipts, private environment mismatch and reviewed new-write compatibility. Caddy regressions cover exact declared nonroot public metadata, owner/group/mode/inode/device/size/hash drift, symlinks/nonregular files, descriptor/path replacement, preserved root-only receipt ownership, exact Caddy identity/mount binding and actual Native context wiring before an ID-bound active-config read. All adapters use synthetic local data; there is no Docker, SSH, network, environment-file or production execution in these tests.
