# Environment and identity contract

The renderer contains deployment identifiers and paths only. Supply restricted `0600` environment files on the VPS; they are never generated from a fleet-wide `.env`, uploaded with release artifacts, or included in images. Bind mounts reject missing paths. The example UUIDs/domains are placeholders, not application rules.

## Shared application services

Set `applicationLayout: "shared"` in the deployment manifest. There is one instance of each of the 18 business services, one client Auth, gateway, UI and maintenance process. Operator services remain separate. Company count changes database bindings, secret mounts and virtual hosts; it does not multiply application processes. CDC and private audit/delivery workers retain their own source/purpose identities and are not consolidated by this change.

A shared process can access all companies in its explicit configuration. The security boundary is verified request identity, per-company credentials, live registry checks and source authorization. It is not OS process isolation between companies. No central organization, projection or history process receives company database credentials.

| Host file | Contents |
| --- | --- |
| `env/shared/auth.env` | Restricted metadata `DATABASE_URL`, client JWT public verification keys for every configured company, service trust keys and existing client Auth settings. No operator signing key. |
| `env/shared/runtime.env` | Restricted metadata `DATABASE_URL`, all client JWT public keys, delegation public keys, scoped service trust keys, `KABIPAY_SERVICE_KEY_ID` and shared business/Finance configuration. No Auth signing keys or tenant database URL. |
| `secrets/shared/<service>/companies.json` | Immutable version-1 company allowlist, mounted as `/run/company-config/companies.json`. One exact entry for every release company, including suspended companies. Services are `auth`, `maintenance`, and each business service name. |
| `secrets/shared/<service>/service/` | Only this service's signing/configuration files, mounted at `/run/service-secrets`. Business processes use `service.key`. Provision the mount directory for Auth/maintenance too, even if empty. |

Use [the Employee configuration example](shared-company.example.json) as a shape example, not a credential file. Every entry has `tenant_id`, a separate `database_url`, `schema`, `public_origin` and `settings`. Include the full release inventory in every service file. Different services must agree on each company's database and schema. Separate databases must use separate LOGIN roles; never use owner/admin/CDC credentials. URLs require `sslmode=verify-full` and the exact registered host/database/schema. Include the PostgreSQL CA in the mounted `config/tls/organization-ca.pem` bundle or use the system trust store. Preserve established tenant UUIDs and schema names. Registry updates do not change the immutable DSN: mismatches block access until a reviewed restart with new configuration.

The renderer supplies `KABIPAY_COMPANY_CONFIG_FILE`, `KABIPAY_CLIENT_JWT_MODE=rs256`, `KABIPAY_REQUIRE_AUTH=1`, service identity and explicit pool limits. Do not set any `KABIPAY_BOUND_*` variable in shared environment files. Missing or invalid shared configuration stops startup; it cannot activate the old derived-schema/global-password resolver. Unknown companies and inactive/deleted companies cannot open or reuse tenant pools. Suspended companies may remain in configuration for inventory completeness but requests and scheduled company work fail closed.

Company secret settings are selected explicitly by UUID; there is no mutable process environment per request. Auth entries require `KABIPAY_CLIENT_JWT_KEY_ID` and `KABIPAY_CLIENT_JWT_PRIVATE_KEY_FILE=/run/companies/<UUID>/auth/client.key`. Each company retains its distinct RSA signing key and each public key is trusted for exactly one company. The Auth process alone mounts `secrets/<slug>/auth` at that company path. Business processes receive only public verification keys. Shared service signing keys are distinct per service; their public trust entries enumerate the configured company IDs for that service. The central organization signer remains separate.

Public key formats remain:

```json
[{"kid":"company-client-v1","tenant_ids":["11111111-1111-4111-8111-111111111111"],"public_key_file":"/run/public-keys/company-client.pem"}]
```

```json
[{"kid":"employee-service-v1","service":"kabipay-employee","tenant_ids":["11111111-1111-4111-8111-111111111111","22222222-2222-4222-8222-222222222222"],"public_key_file":"/run/public-keys/employee-service.pem"}]
```

`KABIPAY_ORGANIZATION_DELEGATION_PUBLIC_KEYS` maps delegation key ID to public PEM file. Client JWT tenant identity selects ordinary requests. Source proxy `X-Organization-Company-Id` is only a routing candidate: command and eligibility handlers verify a signed credential for that exact company before opening its database. Full live organization policy, source installation, business permission and idempotency checks still apply.

One private source proxy serves logical DNS aliases `source-<slug>`. Preserve each `secrets/<slug>/tls/server.pem` and `server.key` covering that alias, plus `private-delivery-client-ca.pem`. The identity/eligibility endpoint is port8443; Employee/Leave/Attendance/Payroll/Performance/Workflow command ports are8444..8449. Port8450 requires mTLS and only serves private delivery/ownership. Existing Finance source endpoints remain on8451/8452. In addition, provision `secrets/shared/source-tls/server.pem` and `server.key` covering `shared-source`. Configure shared Finance origins as `KABIPAY_FINANCE_PAYROLL_URL=https://shared-source:8451` and `KABIPAY_FINANCE_EMPLOYEE_URL=https://shared-source:8452`, with one independent Finance service secret shared only by the intended callers. The Finance protocol authenticates its tenant and intent. No ports are published to the host.

The shared public ingress serves a separate `/config.json` for each company hostname, so Auth/GraphQL/files remain on the company's origin while UI assets and services are shared. Private routes remain blocked publicly. Unknown company hosts have no ingress site.

Employee, Notification and maintenance mount only each declared company's existing `<privateFilesPath>/tenants/<UUID>` directory at `/var/lib/kabipay/private-files/tenants/<UUID>`. Stored relative paths retain their `tenants/<UUID>/...` prefix. Release requires these directories to exist and rejects symlink aliases; it never creates or moves production files. Other services do not receive local file mounts. Preserve cleanup receipts and verify existing absolute cleanup roots before migration. All company application processes share an outbound network; central organization has no company egress network.

`databasePools.perCompany` and `opsPerService` set pool maxima, with zero minimum and idle closure. The manifest must reserve at least `20 * (companyCount * perCompany + opsPerService)` connections in `databasePools.applicationBudget` for the default single-replica application layout. Five companies with limits of one need 120 application connections; this exceeds an unmodified 100-connection PostgreSQL server before other applications are counted. Measure and explicitly size PostgreSQL, reserve connections for operator/organization services, CDC, backups, Finance and RMS, and re-evaluate before scaling replicas. The manifest is an allocation declaration, not proof of the live server setting. Runtime rejects company configurations exceeding its declared pool budget; it never evicts active pools to hide over-allocation.

The release runs a read-only shared configuration preflight in the already loaded event image before starting applications. It checks inventory, consistent database bindings, TLS mode and required company secret files without printing values. Startup also checks exact registry mappings. New company onboarding requires creating/migrating its database and roles, preparing secret/config entries, rendering the complete fleet and rolling shared services after a fresh inventory receipt. No registry-only registration can acquire global credentials.

| `workers/capture.env` | Capture-only metadata role, Kafka capture identity, `CAPTURE_BINDINGS_FILE=/etc/organization/capture-bindings.json`, read-only proxy CA/client key/cert via `CONNECT_CA_FILE`, `CONNECT_CLIENT_CERT_FILE`, `CONNECT_CLIENT_KEY_FILE`. | `workers/control.env` | `CONTROL_BINDING_FILE=/etc/organization/control-binding.json`, `CONTROL_GROUP_ID`, `CONTROL_QUARANTINE_TOPIC=organization.control.quarantine`, Kafka control identity, restricted ClickHouse control writer. No PostgreSQL connection. |

Company workers use `KAFKA_BROKERS=kafka:9092`, exact `KAFKA_GROUP_ID` compatible with provisioned ACLs, `KAFKA_QUARANTINE_TOPIC`, `KAFKA_CA_FILE=/run/secrets/ca.crt`, `KAFKA_CERT_FILE`, `KAFKA_KEY_FILE`, and `POSTGRES_CA_FILE=/run/secrets/postgres-ca.crt`. Provision distinct Kafka certificate principals for inbox, history, reporting, capture, control and each Connect producer. The Kafka binding requires `inboxPrincipal`, `historyPrincipal` and `reportingPrincipal`; each reader can join only its own literal role group. The former shared `consumerPrincipal` is rejected. Never reuse one reader certificate between role secret directories. History/reporting/control add `CLICKHOUSE_URL=https://clickhouse:8443/`, their managed `CLICKHOUSE_USER`/`CLICKHOUSE_PASSWORD`, and the ClickHouse CA file used by `NODE_EXTRA_CA_CERTS`. Separate secret directories are under `secrets/workers/<role>`; mount targets are `/run/secrets`, except archive `/run/archive-secrets`. All public trust key files referenced by archive must be inside its own public verification mount/secret directory, never private source keys.

Organization reporting: `KABIPAY_ORGANIZATION_CLICKHOUSE_URL=https://clickhouse:8443/`, `KABIPAY_ORGANIZATION_CLICKHOUSE_USER=organization_projection_reader`, password file and CA file under `/run/organization-secrets`. Archive: `KABIPAY_ORGANIZATION_ARCHIVE_URL=https://archive:8444`, CA + client cert/key files under `/run/organization-secrets`. Organization service/delegation keys are also there with explicit absolute file variables. Its private TLS sidecar has a separate `secrets/organization/tls` directory.

Archive env must explicitly set `ORGANIZATION_ARCHIVE_ROOT=/var/lib/organization-archive`, `ORGANIZATION_ARCHIVE_KEY_FILE`, `ORGANIZATION_ARCHIVE_KEY_VERSION`, optional versioned `ORGANIZATION_ARCHIVE_READ_KEYS`, `ARCHIVE_BINDINGS_FILE`, `KABIPAY_SERVICE_TRUST_KEYS`, `ARCHIVE_TLS_KEY_FILE`, `ARCHIVE_TLS_CERT_FILE`, `ARCHIVE_CLIENT_CA_FILE`, `POSTGRES_CA_FILE`, and ClickHouse client settings, all using `/run/archive-secrets` for its own secrets. Apply documented UID/filesystem permissions to the archive data directory for the non-root Node image. No automatic data-directory creation is performed.

## Private audit, delivery and history

These files are provisioned independently of the public organization projection/archive workers. All mounts below are read-only; every bind uses `create_host_path:false`. Do not set `ALLOW_ISOLATED_PLAINTEXT` in a release. File contents must match the actual company UUID, source database/schema and current producer generation; a company selector received from a request never creates a binding.

| Process | Env file under `env/` | Host mounts under HRMS root | Required runtime contract / credential scope |
| --- | --- | --- | --- |
| Shared Employee/Leave/Attendance/Expense/Notification/Survey/Analytics and maintenance | `shared/runtime.env` | Each service mounts `secrets/<slug>/private-events/<service>` at `/run/companies/<UUID>/private-events` for every configured company | Set each company entry's `KABIPAY_PRIVATE_EVENT_KEYS_FILE` to its `keys.json`. Private workers require `KAFKA_BROKERS`, `KAFKA_CA_FILE`, `KAFKA_CERT_FILE`, `KAFKA_KEY_FILE` and `PRIVATE_EVENT_GROUP_ID` (not the public worker's `KAFKA_GROUP_ID`). The Kafka admin binding requires distinct `auditPrincipal`, `deliveryPrincipal`, `operatorAuditPrincipal`; set audit/delivery `PRIVATE_EVENT_GROUP_ID` to `<consumerGroupBase>.audit.v1` / `<consumerGroupBase>.delivery.v1`, and operator audit to `organization-operator-audit.v1`, matching the provisioned ACLs. Use distinct provisioned Kafka principals and literal groups. Company audit consumes only `organization.audit.<UUID>`; operator audit consumes only `organization.operator_audit.metadata`. Delivery consumes `organization.delivery.<UUID>`, `.history.<UUID>`, `.work.<UUID>`, `.retry.1.<UUID>` through `.retry.3.<UUID>` and produces work/retry/history/`.dlq.<UUID>` under the same `organization.delivery` prefix. Every required private topic must have exactly partition0. Provision only corresponding read/write/describe/group ACLs; no fleet-wide wildcard or shared audit/delivery credentials.

All private workers/query processes require `CLICKHOUSE_URL=https://clickhouse:8443/`, `CLICKHOUSE_USER`, `CLICKHOUSE_PASSWORD`; renderer sets `NODE_EXTRA_CA_CERTS=/run/secrets/clickhouse-ca.crt`. Worker accounts write/read only their private purpose's chunk/record/checkpoint tables; query accounts SELECT only the corresponding purpose records/coverage. Managed ClickHouse roles are `private_audit_worker`, `private_delivery_worker`, `private_operator_audit_worker` and `private_audit_reader`, `private_delivery_reader`; worker roles have SELECT/INSERT on their own record/chunk/checkpoint/coverage tables, and readers SELECT on record/coverage only. See `hrms-clickhouse/grants/0006-protected-private-history.sql` before provisioning. Query bindings may verify multiple explicit companies with distinct proof keys, but must never contain private event encryption keys. The company worker rejects any encryption key outside its exact UUID/purpose.

The event image runs as `node` (UID/GID1000). Provision each worker/query secret directory so that this container user can traverse that directory and read only its mounted files; use reviewed file ownership with0600 files or a dedicated readable group with0640 files and0750 directories. Keep every purpose/company mount distinct and never make keys world-readable. Host environment files remain0600 because Compose reads them before container startup. Verify the effective container user against the mounted files before release; do not recursively change ownership of existing company or platform data.

History reads also require accepted, restored and unrevoked legacy export coverage in source authority and ClickHouse. Missing coverage is an unavailable result, never an empty history. Provisioning files alone does not satisfy the migration or restore acceptance gates.

## Release and retirement boundary

Only `mode=organization` with a nonempty company manifest is accepted. This release contains no `kabipay-outbox-worker` binary or alternate unbound tenant/HMAC layout. Inventory and provision every active company before cutover; reconcile old pending/uncertain deliveries, export/restore history and complete source authority/reader migration gates before retiring an old worker. The release refuses every running container in the owned `apps` Compose project whose effective command or entrypoint contains the retired `kabipay-outbox-worker` executable, including renamed company workers, absolute paths and shell launches. The old global service-label guard and exact global container name outside that project remain checked. Listing/inspection failure blocks rollout; no container is stopped automatically. Rollback uses separately retained previous release artifacts and reviewed authority state. Company membership/grants/manager relationships remain configurable in the organization workspace; infrastructure identity/key/database provisioning is a separate operator responsibility. First organization creation uses the separately authorized `bootstrap_organization <company-uuid> <organization-name>` CLI and `KABIPAY_ORGANIZATION_BOOTSTRAP_TOKEN`, as described in [the organization service runbook](../../docs/runbooks/organization-service.md#first-organization-and-subsequent-administration); the token must never enter command history or a fleet env file.
