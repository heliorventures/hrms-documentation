# Environment and identity contract

The renderer contains deployment identifiers and paths only. Supply restricted `0600` environment files on the VPS; they are never generated from a fleet-wide `.env`, uploaded with release artifacts, or included in images. Bind mounts reject missing paths. The example UUIDs/domains are placeholders, not application rules.

## Shared application services

Set `applicationLayout: "shared"` in the deployment manifest. There is one instance of each of the 18 business services, one client Auth, gateway, UI and maintenance process. Operator services remain separate. Company count changes database bindings, secret mounts and virtual hosts; it does not multiply application processes. CDC and private audit/delivery workers retain their own source/purpose identities and are not consolidated by this change.

A shared process can access all companies admitted by its deployment inventory and database grants. The security boundary is verified request identity, a restricted service login, live registry checks and source authorization. It is not OS process isolation between companies. No central organization, projection or history process receives company database credentials.

| Host file | Contents |
| --- | --- |
| `env/shared/auth.env` | Restricted metadata `DATABASE_URL`, client JWT public verification keys for every configured company, service trust keys and existing client Auth settings. No operator signing key. |
| `env/shared/runtime.env` | Restricted metadata `DATABASE_URL`, all client JWT public keys, delegation public keys, scoped service trust keys, `KABIPAY_SERVICE_KEY_ID` and shared business/Finance configuration. No Auth signing keys or tenant database URL. |
| `config/companies/<service>.json` | Generated, non-secret version-2 company catalogue, mounted as `/run/company-config/companies.json`. The renderer creates it from the central manifest for `auth`, `maintenance` and every business service. Includes suspended companies for inventory completeness. Do not hand-edit generated files. |
| `secrets/shared/<service>/service/` | Only this service's signing/configuration files, mounted at `/run/service-secrets`. Business processes use `service.key`. Auth and maintenance also require this directory for their stable database configuration. |
| `secrets/shared/<service>/service/database.json` | One stable restricted company-runtime login per service, mounted inside its existing service directory. Renderer sets `KABIPAY_COMPANY_DATABASE_FILE=/run/service-secrets/database.json`. Never uploaded or generated with release artifacts. |

Use [the generated Employee catalogue shape](shared-company.example.json) and [the stable service credential shape](company-database.example.json). Catalogue entries contain `tenant_id`, `public_origin` and purpose-specific secret references, with no database names, schemas or passwords. The central manifest requires each company's existing `clientJwtKeyId`; preserve it during this transition rather than silently rotating keys.

The protected `database.json` has `version:1`, `server_url` and `database_prefix`. Its URL fixes the PostgreSQL host, port, service login, password and TLS options once per service. The URL's database component is only a syntactic placeholder and is never used as a connection fallback. The actual database and schema come from the unique active `kabipay_ops.tenant_database` row. Database names must be lowercase safe identifiers beginning with the configured prefix (for example `company_`); schema names must be safe non-system identifiers. The registered host must exactly match the fixed server host. All service files must agree on host, port and prefix. Use a different restricted LOGIN role per service, granted access to each admitted company database; never use metadata, owner, administrator, migration or CDC credentials. Provisioning and migrations own grants for current and future objects. Runtime roles must not have CREATE DATABASE, CREATE ROLE, superuser, replication, ownership or access to other products' databases. The preflight checks configuration, not actual PostgreSQL role privileges; those require database acceptance checks.

URLs require `sslmode=verify-full`. Include the PostgreSQL CA in the mounted `config/tls/organization-ca.pem` bundle or use the system trust store. Registry rows cannot change credentials, host, port or TLS. Multiple active rows for one company or the same database name for multiple active company mappings are rejected, including alternate host spellings. Accepted database/schema mappings are pinned for the process lifetime: remapping requires a write freeze, reviewed CDC handoff and restart. Registry access is read-only for business services; only authorized provisioning may change mappings. Preserve established tenant UUIDs and schema names.

The renderer supplies `KABIPAY_COMPANY_CONFIG_FILE`, `KABIPAY_CLIENT_JWT_MODE=rs256`, `KABIPAY_REQUIRE_AUTH=1`, service identity and explicit pool limits. Do not set any `KABIPAY_BOUND_*` variable in shared environment files. Missing or invalid shared configuration stops startup; it cannot activate the old derived-schema/global-password resolver. Unknown companies and inactive/deleted companies cannot open or reuse tenant pools. Suspended companies may remain in configuration for inventory completeness but requests and scheduled company work fail closed.

Company secret settings are selected explicitly by UUID; there is no mutable process environment per request. The renderer writes Auth's `KABIPAY_CLIENT_JWT_KEY_ID` from `clientJwtKeyId` and its `KABIPAY_CLIENT_JWT_PRIVATE_KEY_FILE=/run/companies/<UUID>/auth/client.key`. Each company retains its distinct RSA signing key and each public key is trusted for exactly one company. The Auth process alone mounts `secrets/<slug>/auth` at that company path. Business processes receive only public verification keys. Shared service signing keys are distinct per service; their public trust entries enumerate the configured company IDs for that service. The central organization signer remains separate.

Public key formats remain:

```json
[{"kid":"company-client-v1","tenant_ids":["11111111-1111-4111-8111-111111111111"],"public_key_file":"/run/public-keys/company-client.pem"}]
```

```json
[{"kid":"employee-service-v1","service":"kabipay-employee","tenant_ids":["11111111-1111-4111-8111-111111111111","22222222-2222-4222-8222-222222222222"],"public_key_file":"/run/public-keys/employee-service.pem"}]
```

`KABIPAY_ORGANIZATION_DELEGATION_PUBLIC_KEYS` maps delegation key ID to public PEM file. Client JWT tenant identity selects ordinary requests. Source proxy `X-Organization-Company-Id` is only a routing candidate: command and eligibility handlers verify a signed credential for that exact company before opening its database. Full live organization policy, source installation, business permission and idempotency checks still apply.

One private source proxy serves logical DNS aliases `source-<slug>`. Preserve each `secrets/<slug>/tls/server.pem` and `server.key` covering that alias, plus `private-delivery-client-ca.pem`. The identity/eligibility endpoint is port8443; Employee/Leave/Attendance/Payroll/Performance/Workflow command ports are8444..8449. Port8450 requires mTLS and only serves private delivery/ownership. Existing Finance source endpoints remain on8451/8452. In addition, provision `secrets/shared/source-tls/server.pem` and `server.key` covering `shared-source`. Configure shared Finance origins as `KABIPAY_FINANCE_PAYROLL_URL=https://shared-source:8451` and `KABIPAY_FINANCE_EMPLOYEE_URL=https://shared-source:8452`, with one independent Finance service secret shared only by the intended callers. The Finance protocol authenticates its tenant and intent. No ports are published to the host.

The shared public ingress serves a separate `/config.json` for each company hostname, so Auth/GraphQL/files remain on the company's origin while UI assets and services are shared. Private routes remain blocked publicly. Unknown company hosts have no ingress site.

Employee, Notification and maintenance mount only each declared company's existing `<privateFilesPath>/tenants/<UUID>` directory at `/var/lib/kabipay/private-files/tenants/<UUID>`. Stored relative paths retain their `tenants/<UUID>/...` prefix. Release requires these directories to exist and rejects symlink aliases; it never creates or moves production files. Other services do not receive local file mounts. Preserve cleanup receipts and verify existing absolute cleanup roots before migration. All company application processes share an outbound network; central organization has no company egress network.

Companies may share the existing `privateFilesPath` parent such as `/opt/apps/data/private-files`: only their distinct UUID subdirectories are mounted, never the parent. Validation rejects overlapping effective mount sources. Missing tenant directories require reviewed provisioning with the runtime ownership and permissions before startup; the renderer does not create empty substitutes for missing business files.

`databasePools.perCompany` and `opsPerService` set pool maxima, with zero minimum and idle closure. The manifest must reserve at least `20 * (companyCount * perCompany + opsPerService)` connections in `databasePools.applicationBudget` for the default single-replica application layout. Five companies with limits of one need 120 application connections; this exceeds an unmodified 100-connection PostgreSQL server before other applications are counted. Measure and explicitly size PostgreSQL, reserve connections for operator/organization services, CDC, backups, Finance and RMS, and re-evaluate before scaling replicas. The manifest is an allocation declaration, not proof of the live server setting. Runtime rejects company configurations exceeding its declared pool budget; it never evicts active pools to hide over-allocation.

The release runs a read-only shared configuration preflight in the already loaded event image before starting applications. It checks inventory, stable service files, consistent server/prefix, TLS mode and required company secret files without printing values. Startup resolves and pins exact registry mappings; requests recheck them and active company status. Version-1 manually provisioned per-company DSNs remain supported explicitly by the Rust runtime and standalone checker, but this renderer emits version 2 only. Do not mix version-1 and version-2 catalogues in a release.

### Adding a company

1. Create and migrate its separate database through the approved provisioning workflow. Its name must use the established prefix. Complete the shared-helper/catalog migration prerequisites before moving existing production schemas.
2. Grant the existing service LOGIN roles their approved permissions in the new database, including required future-object grants. Keep owner/migration and CDC roles separate. Do not change any existing service password or `database.json`.
3. Register the exact database host/name/schema under the company's UUID in the main metadata registry. Only one active mapping per company and one company per database are accepted.
4. Add the company once to the central deployment manifest with UUID, slug, public host, file path and existing/new client JWT key ID. Rendering generates all 20 company catalogues, mounts and routes automatically.
5. Provision its signing/encryption/history keys, certificates, file directories, public verifier/service trust entries and CDC/ClickHouse bindings. These remain company-specific onboarding requirements; database credentials do not replace them.
6. Recalculate the connection budget, issue a fresh fleet inventory receipt, validate the generated release and perform the reviewed rollout. Current services intentionally admit only the deployed company inventory. A registry insert alone does not activate an unprovisioned company.

The generated private-event references use `keys.json`; Survey/Analytics also use `audit-client.json`, `client.crt`, `client.key`, with `delivery-client.json` for Analytics. Employee uses `delivery-adapter.json`. These are relative to each service's existing purpose-specific company secret mount. Align provisioned filenames before upgrading from version 1. See the private-event contracts below for their contents.

## Release and retirement boundary

Only `mode=organization` with a nonempty company manifest is accepted. This release contains no `kabipay-outbox-worker` binary or alternate unbound tenant/HMAC layout. Inventory and provision every active company before cutover; reconcile old pending/uncertain deliveries, export/restore history and complete source authority/reader migration gates before retiring an old worker. The release refuses every running container in the owned `apps` Compose project whose effective command or entrypoint contains the retired `kabipay-outbox-worker` executable, including renamed company workers, absolute paths and shell launches. The old global service-label guard and exact global container name outside that project remain checked. Listing/inspection failure blocks rollout; no container is stopped automatically. Rollback uses separately retained previous release artifacts and reviewed authority state. Company membership/grants/manager relationships remain configurable in the organization workspace; infrastructure identity/key/database provisioning is a separate operator responsibility. First organization creation uses the separately authorized `bootstrap_organization <company-uuid> <organization-name>` CLI and `KABIPAY_ORGANIZATION_BOOTSTRAP_TOKEN`, as described in [the organization service runbook](../../docs/runbooks/organization-service.md#first-organization-and-subsequent-administration); the token must never enter command history or a fleet env file.
