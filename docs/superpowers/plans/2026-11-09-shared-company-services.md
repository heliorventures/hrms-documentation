# Shared company services implementation plan

**Goal:** One shared instance of each HRMS application service, with an independently credentialed PostgreSQL database per company. Process replicas scale with workload, not company count.

**Approved direction:** The user selected separate company databases and shared services, and authorized completing this change on 2026-11-09. Existing Kafka and ClickHouse installations remain shared. Production data movement is a separate rollout step.

**Architecture:** Each service loads an immutable, operator supplied company configuration file. The file contains explicit database bindings and references to that service's company secrets. A verified client identity or signed organization delegation selects a configured company; the central registry must agree with its database binding. Missing, duplicate, inactive or changed mappings fail closed. No request can supply a DSN, schema, file path or credential. Auth retains distinct company signing keys. Organization policy and source authorization remain mandatory. A shared process can access its configured companies; this is an explicit application trust boundary, while database roles and CDC credentials remain separate.

**Alternatives:** Per-company application stacks were rejected because they multiply business processes. Reusing the legacy global database password was rejected because it loses credential isolation and permits fallback routing. Use shared services with explicit per-company credentials instead.

**Constraints:** Preserve unrelated edits. No commits, production changes or Dart/Flutter commands. The user subsequently approved focused local Rust checks and deployment tests. Keep the legacy development and fixed-company modes for existing fixtures; the new organization deployment selects shared mode explicitly. Never silently downgrade shared mode to legacy configuration. Do not change applied database migrations.

- [x] Make client token issuance, internal command selection, eligibility checks and background sweeps operate on configured companies while preserving signature, policy and source checks.

## Review focus

Unknown or suspended tenant; registry remapping while pools exist; concurrent first requests; wrong-company signed delegation; omitted private key configuration; file paths naming another company; background jobs surviving a per-company failure; connection budget below the declared service/tenant/replica count; stale company environment files reaching shared deployment.

## Validation boundary

Local checks are not migration or deployment proof. Before production, build the new deployment images, rehearse two company databases with distinct roles, exercise concurrent requests and negative tenant access, and measure the connection budget. Preserve a write freeze and rollback receipts for the later database migration.

## Review dispositions

The independent source review identified two availability/cutover issues. Both were addressed:

1. A global initialization lock could make an unavailable company delay another company. Each configured company now owns its initialization mutex; a regression test holds one company's mutex while resolving another company's cached pool.
2. Compose can retain old company application containers as running orphans. Release now refuses the old application service labels before startup and requires an operator-reviewed stop under the cutover plan. It never stops containers or uses `--remove-orphans` automatically.

The file-reader fixture now uses the tenant-prefixed path generated by real uploads and checks that a different tenant cannot read that path. Missing attachment files retain their NotFound response without exposing host paths.

## Remaining production gates

This step changes shared application routing and deployment generation. It does not copy tenant databases, change registry targets, apply migrations, enable logical WAL, restart PostgreSQL or deploy to the VPS. The next phase must resolve the live schemas' shared catalog/helper dependencies and migration history, rehearse database copy and rollback, provision distinct application/CDC roles, reconcile stored cleanup roots, and complete event retirement and restoration acceptance.

The default five-company application allocation reserves 120 PostgreSQL connections even with each pool capped at one. Measure the live limit and other products' usage before sizing. Dedicated company CDC and private-event workers remain; 18 is the business-service count, not the total container count. Earlier image/runtime evidence predates this shared layout.
