### R2-001 — Payroll recalculation discarded the verified company date

Severity: Important. **CLOSED in source; focused executed regression reported by source author.**

Original location: `hrms-svc/crates/kabipay-payroll/src/services/payroll_draft.rs:132`.

Reachable caller: `PayrollAdapter::execute` in `crates/kabipay-payroll/src/organization.rs` handles `PayrollDraft`, constructs the verified organization `PayrollActor`, and calls `calculate_in_transaction`. That function originally read the prior draft using `find(txn, tenant, id)`. `find` calls `find_with_date(..., None)` at line 86. An existing draft with an explicit payment date reaches `payroll_payment_date::refresh_with_date`, whose fallback at `crates/kabipay-payroll/src/services/payroll_payment_date.rs:44` queries `kabipay_ops.tenant` through the company transaction.

Impact: first calculation can succeed, while recalculating the same explicitly dated draft fails when the company database has no operations schema. A shadow operations table could also supply an inconsistent company date. This violates the private verified payroll proof used by the surrounding organization path.

Reproduction conditions: physically separate operations/company databases; an existing payroll draft; nonnull cycle payment date; authorized organization PayrollDraft with the current source revision/version. Source tracing establishes the wrong-database query; this reviewer did not run a real payroll HTTP reproduction.

Refresh: the implementer changed line 132 to `find_with_date(txn, tenant, id, actor.business_date)`. This preserves the source runtime's verified date for the prior-draft read. `services/payroll_draft_date_tests.rs::repeated_existing_review_reads_never_select_ops_with_verified_date` exercises two explicit-date stored-review reads through a strict source-only proxy, rejecting every query except payroll cycle/snapshot reads. The author reports Payroll 74 tests passing in the refreshed four-package run. This establishes the focused helper contract, not a complete real payroll draft/finalization HTTP flow.

### R2-003 — Performance source paths reverse existing transaction lock order

Severity: Important. **CLOSED in refreshed source; focused PostgreSQL lock regressions reported passing.** The original deadlock schedules were established by source tracing, not executed by this reviewer.

Path A: generic source transport locks `performance_participant` `FOR UPDATE` at `crates/kabipay-organization-tenant/src/transport.rs:503`–515 before executing `PerformanceAdapter`. The adapter has no prepare override and then calls `locked_cycle_stage` at `crates/kabipay-performance/src/organization.rs:93`. That helper obtains the `review_cycle` update lock at `crates/kabipay-performance/src/services/performance_workflow.rs:428`.

The existing tenant `submit_manager_appraisal` does the opposite: cycle lock at `crates/kabipay-performance/src/resolvers/mutation.rs:1064`, then participant update lock at line 1067. Existing administrative/lifecycle paths document and use the same cycle-before-participant invariant. An organization ReviewDetail/ReviewSubmit and a local appraisal/stage/admin operation can therefore each hold the row the other needs. PostgreSQL must abort one transaction.

Path B: local `submit_manager_appraisal` holds the participant lock, then calls `performance_management::apply_installed_manager` at `mutation.rs:1070`. That function reads the canonical `management_assignment` `FOR SHARE` at `crates/kabipay-performance/src/services/performance_management.rs:15`. Source relationship installation holds the assignment `FOR UPDATE` at `crates/kabipay-organization-tenant/src/installation.rs:110`, then locks unsubmitted performance participants `FOR UPDATE` at line 132. Concurrent relationship replacement and a local appraisal can deadlock in the participant/assignment pair.

Impact: transient failures for existing tenant appraisal/lifecycle operations and organization reads/submissions or installation; an interrupted organization call remains uncertain until receipt reconciliation. No unauthorized business effect was established.

Reproduction schedule for A: local transaction obtains cycle C; source organization transaction obtains participant P; local requests P; organization requests C. For B: local obtains C and P; installation obtains assignment A; local requests shared A; installation requests P. These schedules follow explicit reachable SQL locks; no concurrent PostgreSQL experiment was run by this reviewer.

Required correction: establish one consistent ordering across transport preparation, existing local performance mutations, relationship installation, canonical-manager reads and source version locks. Adding only a cycle preparation lock to the organization adapter addresses A but leaves B.

Refreshed correction: source transport calls `adapter.prepare` before assignment authorization and generic domain/version locks. Performance preparation takes cycle then participant locks and rejects a changed cycle or employee binding. Relationship installation drains sorted cycles, sorted employee rows and participants before assignment writes, including ENDED/no-capability transitions. Existing local manager resolution uses MVCC reads under the cycle/participant barrier, removing its inverse assignment wait. Metadata actors are installed in sorted principal order; business actor validation is read-only and final display refresh uses `FOR UPDATE SKIP LOCKED`. Retirement drains cycles, employees, pending participants and assignments in source order, samples wall-clock time after draining, and rebinds pending current reviewer snapshots while preserving submitted/future history. New-participant SQL snapshots lock real employee FK targets before assignment fences and re-resolve committed canonical routing.

Supporting executed evidence: source author reports successful four-package tests (Employee 88 passed/2 ignored, Payroll 74 passed, Performance 46 passed/1 ignored, tenant library passed), a fresh real PostgreSQL Performance adapter preparation test passing in 0.52 seconds (local cycle holder can acquire participant/commit; source rejects participant rebinding), and lifecycle author reports the extended actual-0117 PostgreSQL retirement-versus-local-Leave/appraisal regression passing in 1.25 seconds. ## R2-004 — Pending business recovery does not reconcile changed authority epochs

Severity: Important operational recovery issue. **CLOSED in refreshed source/UI with coordinator HTTP RED/GREEN and UI focused evidence. No authorization bypass claimed.**

`roles.rs::replace` increments affected binding versions while retaining allowed capabilities; it has no guard against pending business intents. After a source-committed business command loses its response, replacing/reinstalling that role can therefore leave the original intent uncertain under authority version 1 while the user currently has the same capability under version 2.

`pending_commands.rs` admits that old intent whenever the current `authority(...)` succeeds, without comparing the intent's authority ID/version. `transport.rs` correctly rejects the old receipt when its stored authority version differs from the current policy. Thus both status and cancellation cannot resolve this existing receipt. The UI restores the still-pending reference, and its journal prunes company membership versions/capabilities but does not compare authority epochs or remove references omitted from refreshed pending results. The unresolved reference blocks another command on the resource even after reload.

The correction should reconcile stale pending authority metadata without weakening the source receipt's current authorization checks. Server recovery filtering and the in-memory journal both need to converge; changing only one side leaves the other state path. This is a reachable source-call-chain finding; no new runtime fixture was run by this reviewer.

Final refresh: `pending_commands::same_authority` compares the exact saved/current authority kind, ID and version before returning any recovery reference. Existing metadata configuration epoch guards remain. UI takes a single-use journal snapshot when full pending pagination begins; only a complete successful current response can remove omitted entries. Entry identity and activity generation preserve commands added/replaced/retried/cancelled/status-checked after query start and commands already in flight. Failed/partial/obsolete-owner responses cannot prune. Applied snapshots release captured references, private omitted payloads are discarded, and removal triggers fresh access/source reads without claiming business success or cancellation. Source old-receipt denial remains intact.

Last error-path strengthening reviewed: `recoverable_authority` omits an intent only for an actual Forbidden result or a successful mismatched authority tuple. Database/internal/other errors propagate and fail the page, so the browser cannot mistake an unavailable policy lookup for an authoritative empty recovery snapshot. The coordinator reports fresh session 37503 organization library tests PASS21/1 explicit PostgreSQL fixture ignored, including the revoked-authority versus internal-lookup-failure distinction.

Supporting evidence from coordinator/UI owner: real HTTP RED session 15164 reproduced stale pending recovery after an actual same-manager assignment version 3→4 replacement/install; GREEN session 8306 omitted that obsolete pending reference, allowed fresh source detail and retained exactly one workflow action. UI authority reconciliation RED cases then GREEN passed 6 files/31 tests, including full-pagination failure/no-prune, live/recovered omission, new-command/retry/in-flight/identity races and fresh-read gating. Production UI build/typecheck, normal lint and 1044-file caller check passed. These checks were executed by their owners, not rerun by this reviewer.

### R2-005 — Regular relationship END leaves a stale local appraisal manager

Severity: Important authorization regression. **CLOSED in final source with focused END/expiry/GraphQL and final no-capability-marker PostgreSQL checks reported passing.**

Actual 0115 `organization_bind_review_manager` persists the effective canonical local PRIMARY manager into newly created `performance_participant.manager_employee_id`. Regular `installation::install_relationship` changes an ENDED assignment without rebinding that participant FK; its organization-review snapshot writer runs only for ACTIVE assignments. With no remaining active canonical assignment, `performance_management::apply_installed_manager` leaves the saved participant manager unchanged. Existing tenant `submit_manager_appraisal` then trusts that snapshot via `manager_matches_snapshot` for a local TEAM evaluator.

Reachable example: legacy employee manager B; install current local canonical manager A; create an unsubmitted review participant (its persisted manager becomes A); END and source-confirm that relationship. Employee canonical routing now falls back to B, while A remains the local appraisal's accepted manager. No management-assignment UPDATE trigger was found that repairs this path. This is distinct from detach, whose pending-review rebinding was already fixed.

Required correction: under source installation's established cycle/employee/participant/assignment lock order, recompute unsubmitted current manager FKs for PRIMARY transitions from the effective remaining canonical PRIMARY or actual employee legacy baseline. Preserve submitted appraisal and future-snapshot semantics. The source author is implementing this correction and a focused regression.

Refresh: installation now recomputes pending local manager FKs for prior-current/new-current PRIMARY transitions; current foreign manager resolves to NULL, no current canonical manager uses the actual legacy employee manager, future-only installation does not rewrite early, and submitted rows are excluded. Runtime fallback also uses the actual legacy manager when organization-owned or a retained review marker proves previous managed authority, addressing natural expiry. The author reports real PostgreSQL helper session 22982 PASS (0.63 seconds) for END/legacy/submitted/future/foreign cases and actual GraphQL resolver proxy session 23476 PASS for denying the ended/expired saved manager and allowing the actual legacy manager. Coordinator additionally reports actual SQL executed in PostgreSQL session 8306 covering legacy/current local/foreign suppression/ended fallback.

Final targeted edge raised with both owners: PRIMARY capabilities may omit performance/feedback (for example employee:read only), while 0115 still persists its canonical local manager into a newly created participant. That participant gets no `organization_review_manager` marker. Natural expiry followed by detach could leave the persisted snapshot unchanged after ownership stopped. The final source now recognizes retained PRIMARY history for the exact tenant/subject in the runtime fallback predicate, independent of current ownership or appraisal-capability markers. Thus an expired or retired canonical manager cannot regain authority merely because no review marker exists. Fresh source session 72425 exited 0 and ran two actual PostgreSQL tests successfully in 0.41 seconds: `expired_primary_without_review_caps_cannot_regain_authority_after_detach` and `source_manager_prepare_uses_local_cycle_order_and_rejects_rebinding`. The first executes the actual helper with ownership false, no capabilities/markers, and both expired ACTIVE and ENDED historical PRIMARY rows.
